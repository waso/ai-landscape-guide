# Contributing

Thank you for helping make this guide better. The three most useful contributions, in order:

1. **Corrections** — a wrong date, number, attribution or mechanism. Open a *Correction* issue or a pull request, and include a source.
2. **Clearer wording** — if an entry did not make sense to you, it probably does not make sense to others either.
3. **Missing terms** — an acronym you met in a video or course that is not in the [A–Z index](index-a-z.md).

## How the repository is organised

```
docs/
  index.md                 landing page
  glossary/NN-<section>.md one file per section, one entry per term  ← most contributions go here
  index-a-z.md             GENERATED by scripts/build_index.py — do not edit by hand
  maps/*.md                the seven maps (SVG/PNG + text)
  reference/*.md           translation table, orders of magnitude, math, model families, book map
  guides/*.md              longer explainers (e.g. the Stanford slide)
  assets/maps/*.svg|png    the diagrams
scripts/
  build_index.py           regenerates the A–Z index and data/glossary.json
  check.py                 validates every entry (run by CI)
```

## The entry format

Every term in `docs/glossary/` follows the same shape. Copy it exactly; the checker and the index generator rely on it.

```markdown
### Rotary Positional Embedding (RoPE) <a id="rotary-positional-embedding"></a>
Today's standard positional scheme: encodes position by rotating the Q and K vectors so attention depends on relative distance.

**Why it matters:** Does not extrapolate well on its own, but can be cheaply stretched to longer contexts (position interpolation, NTK-aware scaling, YaRN), which is what makes 128k-token contexts practical.

<small>*Index aliases:* rotary embeddings</small>
```

- **Heading**: the term as people say it, with a short acronym in parentheses if there is one, and a stable id as an empty anchor at the end, `<a id="kebab-case"></a>`. The anchor form works both on the website and when the file is viewed on GitHub. Add ` ★` before the anchor only for the “learn these first” terms (keep that list to about 30).
- ***Also known as***: longer expansions, several acronyms, or product names, comma-separated. Optional; use it when the acronym does not fit in the heading.
- **Definition**: one to three plain sentences. Say what it is and, if useful, who uses it. Numbers and dates are welcome when they help (“Llama-3-8B has 32 query heads and 8 KV heads”).
- ***Why it matters***: one sentence, in the reader’s interest: faster, cheaper, more accurate, safer, or “explains why videos say X”. This line is mandatory.
- ***Index aliases*** (optional): extra names that should find this entry in the A–Z index (nicknames, older names, the way a specific course writes it).

## Style rules

- **Plain words first.** Write for a strong engineer who is new to ML. Prefer an analogy to a formula; if a formula is needed, put it in the [math-notation decoder](reference/math-notation.md) and link to it.
- **One idea per entry.** If an entry needs two paragraphs, it is probably two entries.
- **Place it on the map.** Each term belongs to exactly one section; pick the section by *when in the lifecycle* the term matters, not by how advanced it is.
- **Date what goes stale.** Model names, prices, benchmark scores and “the current best” change every few months; say “as of 2026” or avoid the number.
- **No marketing.** Describe what a thing does, not how great it is.

## Fact-checking

- Every date, number and “who uses what” claim in a pull request should come with a source in the PR description (a paper, a model card, official documentation). Reviewers will ask.
- When you correct something, say what the old text claimed and why it was wrong.
- If you are not sure, say so in the entry (“widely reported but not confirmed by the lab”). Hedged and right beats confident and wrong.

## Before you open a pull request

```bash
pip install -r requirements.txt
python scripts/build_index.py     # regenerates docs/index-a-z.md and data/glossary.json
python scripts/check.py           # must print "OK"
mkdocs build --strict             # must build without warnings
```

CI runs the same three commands on every pull request.

## Adding a map or a reference page

Open an issue first describing what the page would show and why the existing maps do not cover it. Diagrams should be SVG where possible (editable, searchable) and must work in both light and dark mode.
